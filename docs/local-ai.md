# Local AI

Local AI is one part of Bluejay's analysis layer. It explains collected evidence, answers defensive questions and helps users understand individual findings. It does not replace the scanners, parsers, storage model or workflow controls, and it does not receive direct shell access.

## Model roles

Bluejay has three configurable Ollama profiles:

| Profile | Default role model | Base model | Used for |
| --- | --- | --- | --- |
| `chat` | `bluejay` | `gpt-oss:latest` | General defensive chat and command guidance. |
| `analysis` | `bluejay-analyst` | `qwen2.5-coder:latest` | Evidence and log analysis after collection. |
| `explain` | `bluejay-explainer` | `llama3.1:latest` | Plain-language explanations of stored findings. |

The role behaviour and parameters are defined in `Modelfile`, `Modelfile.analysis` and `Modelfile.explain`.

## Create the default models

Install Ollama, then run from the repository root:

```bash
ollama pull gpt-oss:latest
ollama pull qwen2.5-coder:latest
ollama pull llama3.1:latest

ollama create bluejay -f Modelfile
ollama create bluejay-analyst -f Modelfile.analysis
ollama create bluejay-explainer -f Modelfile.explain
```

Use `/status` to confirm that the Ollama executable is available. Use `ollama list` outside Bluejay to confirm that the configured models exist locally.

You can open each role model directly for a quick manual check:

```bash
ollama run bluejay
ollama run bluejay-analyst
ollama run bluejay-explainer
```

## Configure model profiles

View the current profiles:

```text
/model
/config show
```

Change one profile or all profiles:

```text
/config model chat bluejay
/config model analysis bluejay-analyst
/config model explain bluejay-explainer
/config model all qwen3:8b
```

Restore the default role names:

```text
/config reset
```

Changes are written to `data/config.json`. Resetting the configuration changes the names Bluejay will request, but it does not pull or create models in Ollama.

## How analysis works

Tool workflows first save evidence locally. Depending on the command, Bluejay also parses that evidence into deterministic structured findings. The saved scan or log content is then placed into a defensive analysis prompt and sent to the configured Ollama model running on the same machine.

Analysis files must be inside the project directory and cannot exceed 200,000 bytes. Model calls have a 300-second timeout. Generated Markdown is saved under `reports/`.

Model-assisted evidence reports are prompted to cover a summary, key findings, technical details, risk level, plain-language meaning, safe defensive next steps and a hardening checklist.

Normal chat messages use the chat profile and are saved as JSONL transcripts under `chats/`. Bluejay sends a bounded recent context rather than the full unlimited transcript. The current limits are 32 stored context turns and 24,000 context characters, with individual user messages limited to 4,000 characters.

## Local-first boundaries

Using Ollama avoids sending prompts, scans and logs to a third-party AI API. Runtime evidence, findings, reports, configuration and chat transcripts stay under the local project directory unless the user copies or shares them.

This does not make every Bluejay operation offline. Nmap, DNS, HTTP, site and Nuclei workflows communicate with targets or resolvers as part of their checks. Ollama may also need network access when models are pulled for the first time.

## Review model output

Model output is interpretation, not proof. Check claims against the saved source evidence, validate important findings with the system owner, and do not treat a clean analysis as confirmation that a target is secure.

Structured reports from `/report` are built from stored finding records rather than generated by the model. This makes them useful when traceability matters, although the underlying rules and evidence still require human review.
